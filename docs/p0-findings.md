## 1. ⚠️ 修正 §3.3：CUDA torch 的**可用版本与推荐镜像都变了**

### 1.3 🔴🔴 排查陷阱：我第一次误判成"下载卡死"，真凶是我自己的 curl 参数

第一次下载挂了一个半小时纹丝不动，我判断为"镜像/网络问题"。**这个判断是错的。**

真相：curl 的 `--speed-limit 200000 --speed-time 60` 表示"60 秒内平均速度低于
200KB/s 就放弃传输"。那个 wheel 的总长正好是 **2 532 308 219 字节**，而它每次都在
**2 594 590 371 字节**附近停下——一个**超过文件总长**的数字，说明那不是"下载到某处卡住"，
而是 curl 已经放弃、只剩半成品文件的假象。

> **教训**：诊断"下载卡住"时必须先看**文件总长**与**当前长度**的关系。
> 长度超过 Content-Length 就说明判断错了，问题在下载器参数，不在网络。
> 大文件下载不要用 `--speed-limit`，改用「长度校验 + 重试续传」。
> 该逻辑已固化为 `scripts/fetch_wheel.ps1`。

## 3. 🔴 R1 陷阱**已复现**，且比方案描述的更隐蔽

方案 §4.2 说字幕接口"匿名会静默返回空"。我用 `scripts/raw_probe.py` 打印真实响应
后确认：**它比"返回空"更狡猾**。

### 3.1 匿名的真实响应（实测原文）

```
【模式】匿名（无任何 Cookie，仅首页 buvid3）
【视频】超市生存挑战后续！… | cid=42564652953 | 时长=3466s

【1】会话 Cookie:  ['b_nut', 'buvid3']       ← 无 SESSDATA
【2】nav:         code=-101  message='账号未登录'  isLogin=False
【3】/x/player/wbi/v2:  code=0  message='OK'      ← 注意：成功码
```

`data` 里 **`subtitle` 字段是存在的**，内容为：

```json
{
  "allow_submit": false,
  "lan": "",
  "lan_doc": "",
  "subtitles": [],
  "subtitle_position": null,
  "font_size_type": 0
}
```

**这就是陷阱的完整形态**：不报错、不是字段缺失、HTTP 200、`code=0`、`message='OK'`，
只是列表为空。任何"看 code 判断成败"的实现都会把它当成
「该视频没有站内字幕」→ 转入 ASR 兜底或直接产出空文件，全程无异常。

### 3.2 因此定的判定规则（`src/vd/bilibili.py`）

| 情况 | 判定 | 理由 |
| --- | --- | --- |
| 无 `SESSDATA` + 空列表 | `NotLoggedInError`（**无法判定**） | 实测中这正是匿名形态，绝不能说"没有字幕" |
| 有 `SESSDATA` 但 nav `isLogin=False` | `NotLoggedInError` | 本地 Cookie 失效，同样只能"无法判定" |
| 已登录 + 空列表 | `NoSubtitleError`（确认无字幕） | 此时才允许走 ASR 兜底 |
| 已登录 + `subtitle` 字段缺失 | `BiliError`（接口异常） | 字段缺失是接口变更，不是"没有字幕" |
| 有轨道 | 正常返回 | 优先人工字幕（`lan` 不以 `ai-` 开头） |

**关键设计**：登录判据用服务端权威的 `nav().isLogin`，而不是"本地有没有 Cookie"。
本地 Cookie 可能已失效，那时说"没有字幕"同样是错的。

另外，匿名路径特意**不调用 nav**（只看有没有 SESSDATA），少一次请求就少一次撞风控的机会，
并且有一条测试专门钉住这个行为。

### 3.3 已固化为离线回归测试

`tests/test_r1_subtitle_guard.py` 共 8 条测试，不需要网络和登录即可验证上述全部规则。
加上配额与凭证的 13 条，**当前 21 条测试全绿**。

## 4. 🧱 已落地的安全底座（对应级别最高的风险）

这两块不依赖 GPU，所以先做完并加了回归测试。

### 4.1 凭证加密（R11）

`src/vd/storage.py`：

- 密钥（`VD_SECRET_KEY`，在 `.env`）与密文（`data/credentials/*.enc`）**分离存放**
- 按 B 站 UID 一文件，天然隔离；支持一键吊销
- 任何落盘都是 Fernet 密文，**测试显式断言磁盘上不出现明文 `SESSDATA`**
- 缺密钥 / 密钥不符时**明确报错**，不静默降级

### 4.2 配额（R12，规则由工作区主人指定）

`src/vd/quota.py`：

| 登录身份 | 每日次数 | 当日累计时长 |
| --- | --- | --- |
| 主人账号（`VD_OWNER_BILI_UID`） | 不限 | 不限 |
| 其他任何账号 | 3 | ≤ 3 小时 |

实现要点：

- **按登录的 B 站账号计数**，不按浏览器会话 —— 换浏览器、清 Cookie 都不能绕过
- 在**下载音频之前**判定，配额不足时不烧带宽、不占 GPU
- 次数与时长是**两道独立闸门**（这一点在写测试时才想清楚，见下）

> **测试抓到的设计漏洞**：我最初的实现里，时长闸门被次数闸门挡住了——
> 因为"每日 3 个视频"先放行，第 4 个才轮到时长判断，而第 4 个已经被次数拒绝了。
> 也就是说「累计不超过 3 小时」这条规则在**第 3 个视频之前永远不会触发**，
> 一个 3 小时的视频照样能被放行。已修正为两道闸门独立判定，并补了针对性测试。

`tests/test_safety.py` 共 13 条测试全绿（无需网络、无需 GPU）。

## 6. ✅ R2 彻底解除：ASR 路线端到端跑通并实测 RTF

这是方案 §3.3 最担心的一点（"CPU 版 torch 导致 ASR 慢到不可用"）。实测结论：

| 指标 | 实测值 |
| --- | --- |
| 设备 | RTX 4070 Ti 12GB |
| 模型 | FunASR `paraformer-zh` + `fsmn-vad` + `ct-punc` |
| 音频 | 3 分钟中文讲解视频（完整音频，非截断） |
| 转写耗时 | **1.95 s** |
| **实时率 RTF** | **0.0108** |
| 折算 1 小时音频 | **约 0.7 分钟** |
| 逐字稿字数 | 1009 字（**带标点**，语速 5.6 字/秒） |

对比方案 §3.3 对 CPU 版的估算（1 小时视频要转 2-3 小时），**GPU 路线快了约 200 倍**。
RTF 在不同音频上会浮动（另一段样本测得 0.070，仍远低于 1），但量级结论稳固。

**逐字稿质量（人眼判断）**：语义连贯、标点正确，可直接阅读。存在少量同音/专名误识别
（如"花鼓灯"被识别成"花舞灯"、"红油"→"犯油"、末句有重复），属于 Paraformer 的正常表现，
**需要热词表与后处理**——这一点已记入 P1 的调优项。

> ⚠️ **测量方法上的一个修正**：第一版 `scripts/asr_probe.py` 用 HTTP Range 截断下载音频，
> 导致 m4s 文件不完整、解码后只有 12.8 秒，而且随机选中的是唱歌类视频，
> 逐字稿看起来像歌词 —— **几乎让我误判成"ASR 质量不行"**。
> 正式测量必须取完整音频再截断解码时长，脚本已拆分为
> `asr_probe.py`（快速连通性）与 `asr_quality.py`（正式质量与 RTF）。

## 7. 🎯 P0 关键数字：站内字幕命中率 = **60%**

用主人账号的**观看历史**取 20 个视频实测（`scripts/hit_rate.py --n 20`）：

```
样本数            : 20
命中站内字幕      : 12  →  命中率 60.0%
  其中 AI 字幕    : 12
  其中人工字幕    : 0
确认无字幕        : 8
无法判定(未登录)  : 0  ← 必须为 0，否则结果不可信
空字幕(正文为空)  : 0
风控拦截          : 0
样本时长          : 中位 3.7 分钟，合计 359.2 分钟
```

### 7.1 结论：落在「30% ≤ 命中率 < 70%」区间 → **混合策略**

按方案 §6 的判据，ASR **必须是一等公民**；但下面的质量对比给出了一个更精确的策略。

### 7.2 🔍 重要发现一：命中的 12 个**全部是 B 站 AI 字幕，人工字幕 0 个**

已核对原始元数据（`scripts/diag_tracks.py`）：这些轨道的 `lan` 全是 `ai-*`
（`ai-zh` / `ai-en` / `ai-ja` / `ai-es` / `ai-ar` / `ai-pt` / `ai-th` / `ai-id`），
且 URL 都走 `https://aisubtitle.hdslb.com/bfs/ai_subtitle/prod/...`。

**识别逻辑没问题**（B 站 AI 字幕走 `ai_subtitle` 专有路径，人工字幕不走），
但样本里确实一个 UP 主上传的人工字幕都没有。

> 含义：在这个样本上，「站内字幕」≈「B 站自己的 ASR 结果」。
> 所以本地 ASR 的定位不是"更差时的兜底"，而是"B 站没跑 ASR 的那 40% 由我们自己跑"。

### 7.3 🔍 重要发现二：两条路线的短板**完全相同**——专有名词

| 路线 | 实测样本 | 典型错误 |
| --- | --- | --- |
| B 站 AI 字幕 | "deepseek harness 安装教程" | **DeepSeek → DPCARNE / DPC**，`harness` 正确 |
| 本地 FunASR | 中文科普视频 | **花鼓灯 → 花舞灯**，红油 → 犯油 |

**两条路线都不会正确处理专有名词**，而且都不给标点/术语修正。这直接决定了 P1 的设计：

1. **字幕优先不是因为质量更好，而是因为它零 GPU 成本**——同样质量下，
   不占 12GB 显存就是压倒性优势（多人服务下 GPU 是串行瓶颈）。
2. **热词表与后处理必须两条路共用一份**，不能各做一套。
3. 时间戳精度：B 站 AI 字幕是句级、带 `from/to`（本次实测 149 条覆盖 8 分 48 秒），
   与本地 ASR 拼接结果可直接对齐，锚点方案无需分叉。

### 7.4 其他值得记的事实

- 样本里有一个 **262 分钟（4 小时 22 分）** 的视频。它属于"确认无字幕"，
  走 ASR 兜底；这类超长视频正是配额规则（他人 ≤3 小时）要挡的对象。
- 主人的配额实测生效：`配额：不限（工作区主人账号）`，记账正常。
- 全程零风控拦截（限速 0.8s + 会话 Cookie 生效，R4 对策有效）。
- 按实测 RTF 0.0108 估算，这 20 个视频（合计 359 分钟）若全部走本地 ASR，
  纯转写约 **3.9 分钟 GPU 时间**；若走站内字幕则为 **0**。

### 7.5 一个必须记下的测量方法论问题

按 §3.1 的实测，**匿名测出的"字幕命中率"是没有意义的**——匿名下所有视频都返回空列表，
命中率恒为 0%，而这个 0% 纯粹是"没登录"造成的，与字幕覆盖率无关。
所以 §6 P0 里"拿 20 个你常看的视频测命中率"这一步，**前置条件是先完成扫码登录**。
这也是我把 `scripts/hit_rate.py` 里 `not_logged_in` 单独计数、并在非零时明确打印
"命中率**不可信**"的原因。

### 8.1 验收过程抓到的两个**真实缺陷**

写这个验收脚本的价值立刻就体现了——它抓到了两处我自己写的问题：

**① `vd/quota.py` 的 SQLite 连接泄漏（真 bug）**

`with sqlite3.connect(...) as conn:` 是 Python 标准库里少见的反直觉语义：
连接对象实现了 `__enter__/__exit__`，但**只管事务提交/回滚，不关闭连接**。
后果：每次 `check()` / `commit()` / `report()` 都漏一个文件句柄；在 Windows 上表现为
数据库文件被长期占用（`WinError 32`），长期运行还会持续累积句柄。

修复：全部改用 `contextlib.closing()` 包裹，并在 `commit()` 里显式区分
「连接生命周期」与「事务边界」（`with closing(conn)` 套 `with conn`）。
已补回归测试 `test_no_sqlite_handle_leak`：在 Windows 上能删掉数据库文件才算释放。

**② `scripts/fetch_wheel.ps1` 的 Content-Length 解析失效（真 bug）**

原实现用 `[regex]::Match(...)` 只取**第一个** `Content-Length`。
而下载链接会走 301 重定向，第一个响应头是 `Content-Length: 0` —— 于是 `$expected`
恒为 0，「长度校验」形同虚设。
**这正是我在 §1.3 把"下载器主动放弃"误判成"镜像卡死"的根源**：如果当时长度校验有效，
脚本会立刻报告 COMPLETE/INCOMPLETE，而不是留下一个让人猜的中间态。

修复：改为遍历所有匹配取最大值；实测从 `expected=0` 变为
`expected=4157703`，并一次 `COMPLETE` 通过。

> 附带修正一处测试自身的脆弱写法：原先断言 `"--speed-limit" not in 文件全文`，
> 而文件头注释里恰好引用这个坏参数作为反面教材，导致误报。
> 现在断言的是**实际传给 curl 的参数列表**。

## 9. 一个把登录反复搞失败的坑（值得单独记）

现象：连续 3 次"扫码 → B 站 App 提示『二维码已过期』"，看起来像二维码生成有问题。

实际原因是**两个低级的工程问题叠在一起**：

### 9.1 B 站二维码实测只有 **182 秒**有效期

用 `poll_once()` 每 5 秒轮询、记录状态变化，实测：

```
   0.0s  状态=86101  message='未扫码'
 181.9s  状态=86038  message='二维码已失效'
```

而我第一版脚本把轮询窗口设成 240-300 秒，**比二维码寿命还长**。
后果是：脚本还在"等"，但码已经死了，使用者扫到的必然是过期码。

### 9.2 更隐蔽的坑：**同一个文件名被缓存**

脚本每次都把二维码写成 `output/bilibili-login-qr.png`。
于是界面/浏览器展示的可能是**上一轮那张已经死掉的图**——
使用者以为扫的是新码，其实扫的是几分钟前的尸体。
这个坑最难查，因为"生成的码"和"显示的码"是两回事，而日志里一切正常。

### 9.3 修法（两条都必要）

1. **唯一文件名**：`login-qr-<轮次>-<时分秒>.png`，让缓存不可能命中；
2. **倒计时与持续刷新**：`login_qr_loop.py` 在一轮到期后**立刻生成下一轮**，
   不等待使用者"赶上"某一张；`qr_board.py` 提供一个自动刷新的本地网页
   （服务端显式 `Cache-Control: no-store`），随时打开都是当前有效的码。

> 一般化的教训：**当"我生成的"与"对方看到的"之间隔着缓存或异步展示时，
> 必须让两者的对应关系可验证**（唯一文件名、时间戳、显式禁用缓存），
> 否则会把一个显示层的 bug 误诊成服务端的 bug，白排查好几轮。
