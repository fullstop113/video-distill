# P1 取数层：实现与实测记录

> 记录 P1 的设计决策、实测数据，以及**开发过程中被测试抓到的真实缺陷**。
> 前置阅读：[p0-findings.md](p0-findings.md)（P0 的实测结论决定了 P1 的重心）。

---

## 一、P1 要解决什么

方案 §6 给 P1 的定义是「BV → 逐字稿（字幕优先 + FunASR 兜底），含校验、缓存、限速、退避」。

P0 的实测为它定了两个重心：

| P0 实测结论 | 对 P1 的影响 |
| --- | --- |
| 站内字幕命中率 **60%** | 字幕是主干，ASR 兜底覆盖剩下 40%，**两者都必须打磨** |
| 两条路线的专有名词错误**属同一类** | 热词修正表**只能有一份**，不能各做一套 |
| 字幕路线 **零 GPU**、ASR 占满显存 | 取数顺序必须是"先字幕、后 ASR"，且 ASR 必须可缓存 |

## 二、模块结构

```
src/vd/
├─ bilibili.py     B 站接口（含 R1 守卫：未登录 ≠ 无字幕）
├─ credentials.py  大号/小号白名单（取数只能用操作号）
├─ transcript.py   ★ P1 主干：BV → 逐字稿（路由 / 校验 / 缓存 / 修正）
├─ asr.py          ★ FunASR 兜底（模型单例、句级时间戳、时长上限）
├─ hotwords.py     ★ 热词修正（字幕与 ASR 共用一份规则）
├─ cache.py        ★ SQLite 缓存（元信息 / 字幕 / ASR，带 TTL）
├─ quota.py        配额（管理员不限 / 访客 3 次且 ≤3 小时）
├─ storage.py      凭证加密
└─ disclaimer.py   免责声明（单一事实来源）
```

`scripts/transcript_probe.py` 保留为**最小可运行示例**，用于分层排查
（"到底是接口坏了还是逻辑坏了"）；正式流程一律走 `vd.transcript`，避免两处逻辑漂移。

## 三、几个刻意的设计选择

### 3.1 缓存：ASR 结果必须缓存，因为它是唯一"贵"的东西

| 命名空间 | TTL | 理由 |
| --- | --- | --- |
| `video_info` | 7 天 | 元信息基本不变；缓存也降低撞风控的概率（R4 对策） |
| `subtitle` | 30 天 | 字幕生成后很少变 |
| `asr` | 30 天 | **ASR 占 GPU，是整条链路唯一昂贵的步骤** |

选 SQLite 而不是 JSON 文件：需要并发读、TTL 清理、原子写。
（注意 `sqlite3` 的连接必须用 `closing()`——这个坑在 `quota.py` 里已经踩过一次。）

### 3.2 ASR 模型：进程内单例

`scripts/asr_quality.py`（探针）每次调用都 `AutoModel(...)`——
在本机测一次没问题，但放进服务里等于**每个视频都重新加载一遍模型**。
`vd.asr.load_model()` 改成按 `(model, device)` 缓存 + 双检锁，实测模型加载约 24 秒，
单例化后只在首次付出这个代价。

### 3.3 ASR 必须请求**句级**时间戳

这是本轮最容易被忽略、但影响最大的一个点。

不传 `sentence_timestamp=True` 时，FunASR 只返回 `key / text / timestamp` 三个字段，
**没有 `sentence_info`**，于是逐字稿退化成"整片一个时间戳"。

方案 §5.2② 明确要求：*总结与要点里每条结论都要能点回原视频位置*。
一个锚点显然不合格。而**这个退化不会报错**——它会一路安静地进到产物里。

实测对比（同一视频，64 秒）：

| | 段落数 | 产物 |
| --- | --- | --- |
| 传参数前 | **1 段** | 整片一个 `[00:00:00]` |
| 传参数后 | **27 段** | 每句一个时间戳，可点回原位置 |

同时对老版本 FunASR 做了降级：不认该参数时 `TypeError` → 去掉参数重试并记 warning，
而不是直接失败。

### 3.4 热词修正是"上下文窗口"，不是"匹配片段内替换"

规则可声明 `context` 正则。**第一版实现是错的**（见 §5.1），
现在语义是：触发词前后 `window`（默认 12）个字符范围内才做替换。

裸 `DPC` 这种高风险规则必须限定语境——它同时也是别的领域的常见缩写：

| 输入 | 结果 |
| --- | --- |
| `本期视频带来DPCCARNE官方桌面端的安装教程` | ✅ → `DeepSeek` |
| `登录自己的DPCK账号` | ✅ → `DeepSeek` |
| `DPC 官方客户端下载` | ✅ → `DeepSeek` |
| `DPC 是数据保护委员会的缩写` | ✅ 不动 |
| `Windows 的 DPC 延迟过高` | ✅ 不动 |
| `DPC watchdog violation 蓝屏` | ✅ 不动 |
| `这场 DPC 比赛很精彩` | ✅ 不动 |

这些用例已全部固化为回归测试（`test_bare_dpc_rule_is_context_limited`）——
规则表会持续增长，很容易某天放宽过头。

## 四、实测结果

### 4.1 字幕路线（有站内字幕）

`scripts/distill.py BV1NXH661EpG`：

```
[路线] B 站站内字幕（零 GPU）
[产物] output/BV1NXH661EpG.md　1568 字 / 149 段 / 覆盖 00:08:48
[耗时] 1.9s
  · 热词修正 3 处
```

热词修正实际生效的三处（同一篇里 B 站 AI 字幕吐出了**三种**错法）：

```
DPC harness → DeepSeek Harness
DPCCARNE    → DeepSeek
DPCK        → DeepSeek
```

修正后逐字稿：

```
[00:00:01] 本期视频带来DeepSeek官方桌面端的安装教程
[00:00:10] 接下来我们安装DeepSeek Harness
[00:01:05] 还可以登录自己的DeepSeek账号
```

### 4.2 ASR 兜底路线（确认无字幕）

`scripts/distill.py BV14Zhm6oE3p`（64 秒，无站内字幕）：

```
[路线] 本地语音识别（FunASR）（占 GPU）
[产物] output/BV14Zhm6oE3p.md　332 字 / 27 段 / 覆盖 00:01:01
[耗时] 33.1s（其中模型加载约 24s，纯转写约 2s）
  · 确认无站内字幕（allow_submit=False, need_login_subtitle=False）
  · ASR RTF=0.0353 device=cuda
```

### 4.3 缓存效果

| | 耗时 | 路线标注 |
| --- | --- | --- |
| 首次 | 1.9s | B 站站内字幕 |
| 第二次 | **0.6s** | B 站站内字幕（**缓存**） |

### 4.4 空产物守住了

用 16 秒无语音视频（`BV1Arh26SEde`）测 ASR 路径，FunASR 返回 `empty speech`：

```
❌ BV1Arh26SEde 的 ASR 兜底 产出的逐字稿过短（有效字符 0 < 下限 80）→ 判为失败。
   宁可报错，不产出空文件。
```

**没有产出空文件**，符合方案 §5.2③。

## 五、开发过程中被测试抓到的两个真实缺陷

这一节比"功能已实现"更有价值——两个 bug 都**不会报错**，只会安静地产生错结果。

### 5.1 热词上下文规则永远匹配不到（功能静默失效）

**原实现**：用 `ctx.subn()` 在**匹配到的片段内部**做替换。

**问题**：上下文正则匹配到的往往只是一个触发词（如 `包子`），
而误识别词（如 `犯油`）在它**外面** —— 于是替换永远不发生，
规则**看起来配了、实际完全不起作用**。

**修复**：改为「上下文窗口」——找出所有触发点，向两侧各扩 `window` 个字符，
在合并后的区间内替换。并补测试钉住"该改的改、不该动的不动、窗口有界"。

### 5.2 失败结果被写进缓存（绕过校验）

**原实现**：先 `cache.put("asr", ...)`，后 `_validate(text, ...)`。

**问题**：`empty speech` 这类失败产物被写进了缓存。下次请求读缓存直接返回空内容，
**并且绕过了校验**——等于用缓存把"绝不产出空文件"这条硬规则绕过去了。
更糟的是它表现为"第二次比第一次快"，看起来像优化生效。

**修复**：把 `_validate` 提到写缓存之前。补测试
`test_failed_asr_result_is_not_cached` 与 `test_successful_asr_result_is_cached`。

> 一般化的教训：**"校验"与"持久化"的顺序是有语义的**。
> 先持久化再校验，等于给失败结果发了一张免检通行证。

| 任务队列（GPU 串行调度） | ⏳ 未做 | 方案 §5.2① 要求。目前 `distill.py --no-quota` 之外的调用是同步阻塞的；多用户并发需要队列，属于 P3 Web 层的前置 |

## 八、一个被我自己搞错的"待办"（值得记下来）

**现象**：`login_from_browser.py` 写好后，我在汇报里把它说成了
"你方便时在 Edge 里用小号登录一次，我再跑这个脚本"。

**为什么这是错的**：扫码登录**早已成功**，操作号的凭据一直在正常使用
（凭据文件名即其 UID，属本机私密数据，不在文档里展开），
P1 的全部实测都跑的它。登录是**一次性动作**，不存在"再登录一次"的需求。

**错在哪一步**：我原本在排查"B 站 App 扫不出码"（服务端从未收到扫码事件，
属 App 端问题）。但在准备绕行方案的过程中，**目标悄悄从"绕开 App 扫码"
变成了"让用户再登录一次"**——后者是我自己制造出来的需求。

**正确表述**：备用登录路径**已就绪，暂时用不上**；只有当 `SESSDATA` 真的失效、
且 App 扫码仍不可用时才需要它。

> 教训：准备"绕行方案"时，要回头确认**原问题是否已经不存在**。
> 绕行方案一旦写好，很容易被当成新任务派出去，反而给用户增加了不必要的工作。
