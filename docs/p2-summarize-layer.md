## 一、P2 要解决什么

方案 §5.2② 给 P2 定了一条硬要求：

> 逐字稿要带时间戳锚点。总结与要点里**每条结论都要能点回原视频位置**。
> 这不只是体验问题 —— 它决定了产物能否被信任和复用。

所以本层的验收标准不是"总结得好不好看"，而是：
**每条要点是否真的能点回原视频的对应位置。**

## 二、两个必须先确认的接口事实（都实测过）

### 2.1 JSON 输出：有官方明说的失败模式

DeepSeek 的 JSON 模式（[官方文档](https://api-docs.deepseek.com/zh-cn/guides/json_mode)）有三条约束：

1. 要设 `response_format={'type': 'json_object'}`；
2. **prompt 里必须出现 "json" 字样并给出格式样例**；
3. **官方明说**："在使用 JSON Output 功能时，API 有概率会返回空的 content。"

第 3 条决定了实现必须**带重试**，不能把空 content 当成"没有内容"接受。
`DeepSeekClient.json_call()` 对空 content 与非法 JSON 都重试，并在耗尽后明确抛错。

### 2.2 思考模式默认开启——这是个会静默吃钱的坑

[官方文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode)：思考模式**默认打开，且 effort 默认为 high**。

这解释了 P0 时我遇到的一个现象：用 `max_tokens=8` 发请求，flash 与 v4-pro 都返回**空字符串**。
当时我以为是接口问题，实际是**思考内容把 8 个 token 全吃光了**。

对 P2 的影响：我们做的是"抽取 + 压缩"，不是难题推理，思考的收益很低而成本是实打实的。
所以显式关闭：

```python
extra_body={"thinking": {"type": "disabled"}}
```

## 三、策略：不要为了架构好看而无条件 map-reduce

`deepseek-flash` 上下文是 **1M**，而 P0 实测 1 小时中文视频的逐字稿**约 10400 字**。
也就是说**绝大多数视频根本不需要分片**。

成本差（空闲时段，实测价目）：

| 方案 | 1 小时视频成本 |
| --- | --- |
| 一次过 | **¥0.022** |
| map-reduce（放大 2.5 倍输入） | ¥0.042 |

所以默认 `auto`：全文 ≤ `single_pass_chars`（默认 6 万字）就一次过，超了才分片。
无条件 map-reduce 等于白花一倍的钱，还多一次调用失败的机会。

## 四、锚点校验：这是本层最重要的 30 行代码

模型会**编造时间戳**。如果不管，产物里就会出现"看起来能点、点过去是别的内容"的锚点——
这种产物比没有锚点更糟，因为它**假装可追溯**。

`validate_points()` 的做法：

1. 把模型给的 `HH:MM:SS` 解析成秒；
2. 与逐字稿里**真实出现过的 segment 起始时间**比对，允许 2 秒误差（模型会取整）；
3. 对不上的锚点**直接丢弃**；
4. 若一条要点所有锚点都被丢掉，**保留文本但标注"⚠️ 无可靠出处"**——
   宁可让用户看到"这条没出处"，也不给一个假位置。

实测效果：单次总结 12/12 条有锚点、map-reduce 16/16 条有锚点，**丢弃 0 个**。

## 五、实测结果

### 5.1 单次全文（8.98 分钟视频，站内字幕）

```
[逐字稿] 复用产物 BV1NXH661EpG.md（147 段）
  · 单次总结（全文 1549 字）
[策略] 单次全文　1 次调用　4.1s
[要点] 12 条，其中 12 条带时间戳锚点
[成本] ¥0.0038（输入 2458 / 输出 892）
```

**锚点精度抽查**（人工核对锚点处的原文）：

| 要点 | 锚点 | 该位置的逐字稿原文 |
| --- | --- | --- |
| 安装前需关闭 web ui | `00:00:06` | `安装之前先确认已经关闭了web i` |
| 对话/SK 可继承、插件不可 | `00:00:50` `00:00:55` | `一般情况下它会自动继承对话和SK的` / `但是插件无法去继承` |
| 删除 web ui 相关文件 | `00:07:21` | `最后如果想要删除web ui的相关文件` |
| 结论：开放自由 | `00:07:50` `00:07:51` | `非常开放` / `非常自由` |

锚点不是"大概在这一段"，而是**逐句对应**。

### 5.2 分片 map-reduce（15 分钟视频）

```
  · 分片总结：1 片（全文 2983 字）
  · 合并 28 条分段要点
[策略] 分片 map-reduce　2 次调用　12.7s
[要点] 16 条，其中 16 条带时间戳锚点
[成本] ¥0.0222（输入 7632 / 输出 3645）
```

map 阶段产出 28 条 → reduce 合并为 16 条，**锚点在合并过程中全部保留**。
要点里带具体数字（各英雄得分 469 / 655 / 1076 / 36 / …），说明模型确实在读内容而非泛泛而谈。

### 5.3 上下文硬盘缓存生效（值得注意的省钱点）

同一视频第二次总结：

| | 输入 tokens | 缓存命中 | 成本 |
| --- | --- | --- | --- |
| 首次 | 2491 | 0 | ¥0.0061 |
| 第二次 | 2458 | **2304** | **¥0.0038** |

system prompt 稳定不变，于是 DeepSeek 的上下文硬盘缓存能命中——
**缓存命中价是未命中的 1/50**（空闲时段 0.02 vs 1.0 元/百万）。
这也是为什么 prompt 要写成常量而不是每次动态拼接。

## 六、成本总账（实测）

| 视频 | 时长 | 逐字稿 | 策略 | 调用 | 成本 |
| --- | --- | --- | --- | --- | --- |
| BV1NXH661EpG | 9.0 分钟 | 1549 字 | 单次 | 1 | ¥0.0038 |
| BV1zQRWBTEhU | 15.1 分钟 | 2983 字 | map-reduce | 2 | ¥0.0222 |

按此推算 1 小时视频：单次约 **¥0.01-0.02**，与方案 §5.3③ 的估算（¥0.1-0.3）相比**更低**。
方案那个估算偏保守，原因是它假设了更大的 map-reduce 放大倍数。

> 结论重申（与方案一致）：**真正吃预算的从来不是 LLM**。

## 七、开发过程中被测试抓到的问题

### 7.1 逐字稿自身的质量缺陷：近邻重复没被去掉

锚点抽查时顺带发现了逐字稿的问题：

```
[00:07:19] ♪ 我也许有我 ♪          ← BGM 歌词混进逐字稿
[00:07:30] 找到deep sekai的依赖     ← 同一句重复
[00:07:30] 找到deep sekai的依赖
[00:07:52] ♪ 一回头是我 ♪
```

P1 的去重只处理**紧邻**重复，而这两句中间隔了别的行，所以漏掉了。
已改为**时间窗口内查重**（默认 10 秒），实测该句只剩一条，段数 149 → 147。

> 值得记的一点：**锚点校验顺带成了逐字稿的质量探针**——
> 为了核对锚点必须去读原文，于是原本不会注意到的重复与噪声就暴露了。

### 7.2 测试自身写错了两处（记录以免重犯）

| 问题 | 说明 |
| --- | --- |
| 假 client 按调用顺序弹响应 | 要求测试预知分片数，分片逻辑一改就假失败。改成**按 prompt 类型响应** |
| 只压 `chunk_chars` 没压 `single_pass_chars` | 全文仍小于阈值时走单次，测试"通过"但没测到 map-reduce。两个都要压 |

### 7.3 一处校验反而证明了它有效

写假数据时 overall 只有 36 字，被 `MIN_SUMMARY_CHARS=40` 拦下。
这不是 bug —— 是校验按设计工作。把假数据加长即可。

## 九、产物格式改版（用户反馈驱动）

用户看完一份真实产物后问"总结的格式需不需要优化"。分析实测产物
（`BV1dFem67EYt`，21 分钟视频，13 条要点）后，结论是
**准确性没问题，问题在版面结构**。

### 9.1 先确认哪些是好的（不该动）

| 指标 | 实测 | 结论 |
| --- | --- | --- |
| 锚点命中 | **5/5**，偏差 1-2 秒 | 可靠 —— 这是产物最重要的性质 |
| 分类 | 事实 5 / 论据 4 / 结论 3 / 方法 1 | 语义正确，不是乱贴标签 |
| 时间顺序 | 首个锚点**单调递增**（1分 → 21分） | 视频是"回顾发展史"，时序正是它的叙事骨架 |

**所以要点部分一个字没动。** 特别是不按 category 重排 ——
那会破坏契合内容的时间线；分类标签用于**筛选**，不是排序。

### 9.2 发现的真错误（不是风格问题）

**① 声明写错了对象。** 总结文件里写着「本**逐字稿**由个人自用工具生成」——
P2 直接复用了逐字稿的模板。**给使用者看的法律文本说错自己是什么，比排版问题严重。**
修复：`artifact_header(..., kind=...)` 参数化。

**② 代词错误。** 「暴雪是否愿意持续为**他**承担未来」——原文说的是"游戏"。
这类错误**锚点校验抓不到**（时间戳是对的，是措辞失真），
已在三处 prompt 里显式加入"人称要准确，不要把游戏/视频/项目写成他/她"。

### 9.3 版面问题与改法

| 问题 | 实测 | 改法 |
| --- | --- | --- |
| 总结是单一长段落 | 295 字符、1 段、最长句 91 字 | **本地按句重排成多行**（只加换行，不改字） |
| 头部开销过重 | 元信息 5 行，占 **17.6%**，正文只占 13.9% | 压成 **1 行** |
| 没有速览 | 无 | 新增 `## 速览`：一句话（模型产出，≤60 字） |
| 没有导航 | 13 条要点跨 21 分钟，无法判断跳到哪 | 新增 `## 关键时间轴`：**5-10 个里程碑** + 可点击跳转 |
| 生成记录缺关键信息 | 只有 token 数 | 元信息行加入**视频时长**与逐字稿字数 |

### 9.4 改版后实测（同一视频）

| 项 | 改版前 | 改版后 |
| --- | --- | --- |
| 声明主语 | ❌ 本逐字稿 | ✅ 本总结 |
| 头部 | 5 行 / 17.6% | **1 行** |
| 总结正文 | 1 段 | **6 段** |
| 关键时间轴 | 无 | **10 个里程碑**，全部可跳转 |
| 成本 | ¥0.0174 | ¥0.0189（**+8.6%**） |

**时间轴质量抽查**（10/10 精确命中，精确到句子）：

| 时间轴条目 | 该时刻的逐字稿原文 |
| --- | --- |
| `00:02:11` 2009年Valve招走冰蛙 | `2009年` → `valve把冰蛙招了过去` |
| `00:02:43` 2009年英雄联盟上线 | `2009年英雄联盟正式上线` |
| `00:03:44` Valve申请DOTA商标 | `valve申请注册DOTA商标` |
| `00:11:47` 2017年风暴英雄2.0上线 | `2017年风暴英雄2.0上线` |
| `00:13:31` HGC突然取消 | `2018年12月13日` → `暴雪发出一篇公告` |

模型选的是**事件发生的那一句**，不是"大致段落"。

### 9.5 时间轴也要防编造

与要点锚点同一原则，但判定更宽松一点：时间点只需落在 `[0, 视频时长+30s]`，
不必精确命中某个 segment 起点（"跳到某一刻"本来就允许几秒偏差）。
另外强制**按时间升序**、条数上限 12、短语超 40 字截断 ——
时间轴的用途是"5 秒内决定跳到哪看"，十几条无序列就不是时间轴了。

### 9.6 一个纯本地排版函数，也踩了两次

`_split_sentences()` 只加换行、不改一个字（有测试断言"拼接后与原文完全一致"）。
即便如此还是返工了一次：

- 第一版按"行短于 target/2 就并回上一行"写，结果并完可能超长，
  而超长检查只在 >110 时触发，于是 82 字的行照样留着；
- 第二版改成"贪心累积到 target"，并让**没有句末标点的长文本**
  也能在分号/逗号处切开（口语转录里很常见）。

顺带删掉了因此变成死参数的 `hard_max`。

> 教训：**"只加换行不算改内容"是对的，但排版逻辑本身照样会有 bug**。
