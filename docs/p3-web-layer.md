## 一、P3 要解决什么

方案 §6 给 P3 的定义是「FastAPI + 前端：扫码登录页、提交任务、进度、结果展示与下载；
**账号体系与配额限流**（托管模式新增）」。

方案 §5.2① 另外定了一条架构前提：

> **GPU 是串行资源，必须有任务队列。**
> 需要一个队列（建议先用简单的进程内队列 + SQLite 持久化，**别一上来上 Celery/Redis**）。

---

## 二、为什么是「SQLite + 单工作线程」而不是 Celery/Redis

方案自己给了答案，本项目让理由更硬：

**队列的并发度恒为 1。** FunASR 占满显存，多人同时提交不能并发转写。
一个并发度永远是 1 的队列，用不上 Celery 的分布式调度、重试编排、多 worker 能力，
却要额外背一个 Redis 进程和一套部署复杂度。

所以：

| 需求 | 实现 |
| --- | --- |
| 持久化（重启不丢） | SQLite `tasks` 表 |
| 串行 | **一个**工作线程 |
| 原子认领 | `UPDATE ... WHERE status='queued'` 的 rowcount 做乐观锁 |
| 崩溃恢复 | 启动时 `requeue_stale()` 把心跳超时的 RUNNING 放回队列 |
| 可观测 | 状态/阶段/进度/错误全在表里，`/healthz` 直接查 |

## 三、模块结构

```
src/vd/
├─ pipeline.py   ★ 管线编排（CLI 与 Worker 共用，避免三份会漂移的逻辑）
├─ tasks.py      ★ 任务存储：队列、状态机、原子认领、崩溃恢复
├─ worker.py     ★ 单线程消费者
└─ web.py        ★ FastAPI 应用：页面、扫码登录、任务、下载

scripts/serve.py     启动服务（拉起 worker + uvicorn）
tests/acceptance_p3.py  端到端验收（真实路由 + 真实 worker）
```

**`pipeline.py` 的存在理由**：在它之前，`distill.py` 和 `summarize.py` 各自写了一遍
"取数 → 总结 → 落盘"，Worker 需要**第三遍**。三份会漂移的编排是维护灾难。

## 四、被真实服务"打脸"后补上的安全缺口

这一节是本文最有价值的部分。

### 4.1 缺口：没有会话也能提交任务

**最初实现**：`POST /tasks` 只检查 `load_operator_credentials()` 是否可得。

**问题**：磁盘上的操作号凭据是**长期存在**的。于是任何能访问该端口的人
（包括以后把服务绑到内网时）都能直接提交任务 —— **无需登录，烧的是主人的配额和 GPU**。

**为什么单元测试没抓住**：测试用的是隔离的临时目录，里面恰好**没有**凭据，
所以测试看到的是 401/409 的拒绝路径，而真实环境走的是放行路径。
**测试环境的隔离反而掩盖了真实环境的问题。**

**修复**：提交任务必须有**会话 Cookie**，会话只能通过扫码登录获得。
并补了三个测试（`test_task_creation_requires_login_session`、
`test_task_page_requires_login_session`、`test_task_page_rejects_other_users_task`）。

> 教训：**"测试通过"不等于"真实环境安全"**。
> 当被测对象依赖外部状态（磁盘上的凭据、环境变量）时，
> 测试隔离掉的正是生产环境里存在的那部分输入。
> 这次是靠**真的把服务跑起来打接口**才发现的。

### 4.2 设计错误：操作号被无条件当成管理员

`admin_uids()` 原本无条件把 `VD_OPERATOR_BILI_UID` 并入管理员集合。
后果：**没法让一个非管理员账号专门负责取数** —— 一旦设成操作号，
它就自动获得提交权限与不限配额。

但"用谁的凭据取数"和"谁能提交任务"**是两件独立的事**。
已加显式开关 `VD_OPERATOR_IS_ADMIN`（默认 `true`，需要严格分离时设 `false`）。

### 4.3 队列顺序用了秒级时间戳

`created_at` 只有**秒级精度**，同一秒创建的两个任务排序不确定，
于是"你在队列第 2 位"可能算成第 1 位。**队列位置是给用户看的，错了就是骗人。**
已改为自增 `seq` 列，所有排序与比较一律用它。

### 4.4 完成后再提交会重跑一遍

`find_active()` 只复用"排队中/运行中"的任务，所以**连点两次提交会跑两遍**，
第二遍白花 LLM 费用。已加 `find_reusable()`：复用活跃任务 + 刚成功完成的任务
（窗口默认 600 秒，`VD_TASK_REUSE_SECONDS` 可调，设 0 关闭）。
**失败的任务永远不复用**，否则就没法重试了。

## 五、安全边界（不可被 Web 层绕过）

| 边界 | 实现位置 |
| --- | --- |
| 取数只能用操作号凭据 | `vd.credentials` 白名单（Web 层**不重新实现**它） |
| 提交任务必须有会话 | `web._require_session()` |
| 未受邀账号不能提交 | `web.can_submit()` + `VD_INVITED_UIDS` |
| 只能看自己的任务 | `task_page()`（管理员除外） |
| 下载不能路径穿越 | `/files/{name}` 只接受 output 下的 `.md` |
| 不回显 API key | `/apikey-check` 只返回前缀与末四位 |

**一个诚实的说明**：`VD_INVITED_UIDS` 是**前瞻性**配置。
当前取数凭据总是操作号，而操作号在默认设置下就是管理员，
所以"非管理员且未受邀"这条 403 分支**在默认配置下不可达**。
它会在将来支持"多个使用者各自登录"时真正生效。
这一点写进了测试注释，而不是写一个永远不会失败、也没测到东西的测试。

### 为什么验收脚本不加"开发模式跳过登录"

为了能提交任务，最省事的做法是加 `VD_DEV_NO_AUTH=1` 之类的开关。
**那是把测试便利变成长期安全风险** —— 开关会被忘记关掉，而且一旦存在就会被依赖。

所以 `tests/acceptance_p3.py` 用 `TestClient` 在**进程内**走真实路由，
会话通过 `web._login_for_test()` 注入（与生产会话结构**同一个定义**，
避免测试自己拼 dict 导致字段改名后测试照过），
任务由**真实 Worker** 消费，产物写到临时目录。

```powershell
.\.venv\Scripts\python.exe scripts\serve.py --port 8788
#   --no-asr          只走站内字幕（不加载 ASR 模型，省显存）
#   --host 0.0.0.0    对外开放（此时务必确认邀请名单与免责声明）
```

启动时会做几项硬检查并 warning：未配置操作号 / 未配置大号 / 操作号尚未登录。

### 已知限制

| 限制 | 说明 |
| --- | --- |
| 会话存在内存 | **重启服务需重新扫码登录**（邀请制下使用者很少，不值得引入完整用户表） |
| 不支持 `--reload` | reload 会再起一个进程 → 两个 worker 抢同一个队列。启动脚本里直接拒绝 |
| 无 HTTPS | 面向内网/本机。对外部署时必须加反代与 TLS |
| 无速率限制 | 目前靠配额与队列串行；对外暴露前需要补 |

## 九、调试阶段被用户发现的三个问题（都已修）

用户实际打开页面后报的三个问题，全部是**真 bug**，而且都是"测试全绿但功能不可用"的类型。

### 9.1 二维码从来没显示出来过（参数名不匹配）

```
POST /login/start   -> 200 ok=True key=9Ba1UG8idJmF
GET  /login/qr.png?k=...  -> 404        ← 出图失败
```

前端传 `?k=`，后端读的是 `key`。**参数名不匹配导致二维码永远是 404**，
而当时没有任何测试覆盖这条路径 —— 测试只测了"未知 key 返回 404"，
恰好把这个 bug 当成了预期行为。

修复：统一用 `key`，并补测试 `test_login_qr_png_works_with_key_param`
断言真的返回有效 PNG（检查 magic bytes），以及
`test_login_page_uses_matching_param_name` 断言前端参数名与后端一致。

### 9.2 "开始蒸馏"后被要求扫码，但页面上没有登录入口

这是**设计自相矛盾**：最初实现了"扫码登录 + 会话"，
同时又要求"提交任务必须有会话"，而**本机磁盘上本来就有操作号凭据**。于是：

- 首页显示提交表单（因为凭据在）
- 提交时被拦（因为没有会话）
- 页面上又找不到登录入口（因为后端认为已经"登录"了）

根因是把"是否需要登录"和"凭据是否可用"混为一谈。正确做法是按**访问来源**决定：

| 访问来源 | 是否需要扫码 | 理由 |
| --- | --- | --- |
| 本机（127.0.0.1 / ::1） | **不需要** | 能访问本机端口的人本来就能直接读 `data/`，登录只是仪式感 |
| 局域网 / 公网 | **需要** | 此时登录才是真正的访问控制 |

判定基于 **socket 对端地址**（`request.client.host`），
并有一条测试专门钉住"伪造 `Host: localhost` 不能白拿本机待遇"——
Host 头是客户端可控的，用它做安全判定等于没做。

局域网免登录可用 `VD_WEB_TRUST_LAN=true` 显式打开（默认关）。

### 9.3 免责声明里的 Markdown 标记原样显示给用户

`**不对外开放注册**` 这类标记直接显示，因为最初只把换行换成了 `<br>`。
**给使用者看的法律文本不能是半成品标记**，那会直接削弱它的严肃性。

改成真正的 HTML 结构（`<h3>/<h4>/<ol>/<li>/<strong>`），过程中又踩了两个坑：

1. **跨行的粗体**：原文 `10. …**不得对外发布、转载、再分发，` /
   `    不得用于任何商业用途**。` 的 `**` 跨越两行，
   逐行转换时两行各剩一个星号，谁也配不上对。→ 先把续行拼回上一条。
2. **缩进的编号条目不是续行**：免责声明原文的条目本身就带 2 空格缩进
   （`  1. …`），用"缩进 = 续行"的宽松判定会把**所有条目粘成一大段**。
   → 判定改为"缩进的编号条目/标题/提示都是新条目"。

顺带修掉 `disclaimer.py` 里一处**文案 bug**：操作号说明被写成了
`9. 本服务仅使用操作号凭据…`，插在第 8 条后面会出现两个"9."。

已补 5 条渲染测试（无残留标记、跨行合并、条目不粘连、提示成块、标题结构化）。

### 9.4 界面太简陋

原先是纯文本堆叠。现在是统一配色的卡片式界面：状态药丸、进度条、
要点用可点击的时间戳跳回原视频（`?t=<秒>`）、队列位置、配额进度条，
以及独立的服务状态页 `/status` 与配额页 `/quota`
（原先这两个只是 JSON 接口，用户点到的是一片纯文本）。

## 十、用户实测发现的第四个问题：受限视频被误报为"接口异常"

用户在网页上提交一个视频，得到：

```
任务未能完成: BiliError: playurl 未返回 DASH 音频流
```

用户自己猜到了原因（"可能是充电视频"），而且**猜对了**。实测确认：

```
is_upower_exclusive = True            # 充电专属
is_ugc_pay_preview  = True            # 仅预览
preview_toast       = '为创作付费，购买观看完整视频|购买观看'
playurl: code=0, message='OK', 无 dash, 有 durl[1 段]
durl[0].length      = 249987 ms       # 250 秒
视频真实时长         = 1749 s          # 29 分钟
```

### 10.1 真正的问题不是"没返回音频"，而是**我的代码只认一种格式**

`code=0`、`message='OK'`，B 站**给了东西** —— 一段可正常播放的 250 秒预览（含 aac 音轨，
ffmpeg 实测可解）。旧实现只检查 `dash.audio` 是否为空，于是把

- 权限受限（充电/付费预览）
- 真的没有音频轨
- 接口结构变更

三种完全不同的情况，糊成同一句 `BiliError("playurl 未返回 DASH 音频流")`。
**它们的处置方式完全不同**（有的该提示用户、有的该降级、有的该重试），
糊在一起等于让用户和排查者都在猜。

这与我在 R1 里批判的"静默失败"是同一类毛病 —— 只不过这次犯在自己的代码里。

### 10.2 🔴 更危险的是"顺手加个 durl 降级"

如果只做格式降级而不校验时长，就会生成一份 **250 秒的逐字稿**，
而使用者以为它是 29 分钟视频的。**这是比报错严重得多的事故**：
报错用户至少知道失败了，而残废产物会被当作成果使用。

所以修复分两层：

| 层 | 做法 |
| --- | --- |
| **提前识别** | `video_info()` 补查 `is_upower_exclusive` / `is_ugc_pay_preview` / `preview_toast`，已知受限就直接拒绝（省一次请求） |
| **硬校验** | `audio_url()` 返回 `(url, 媒体流时长)`；`transcribe_video()` 把流时长与视频时长比对，**低于 95% 即判为预览片段并失败**；解码后再比对一次实际音频长度 |

异常也分成三类，各自可读：

| 情况 | 异常 |
| --- | --- |
| 充电专属 / 付费预览 | `RestrictedVideoError` |
| 接口正常但确实没有音频 | `NoAudioTrackError` |
| 既有 dash 又有 durl 都没有 | `AudioUnavailableError` |

用户现在看到的是：

```
该视频受权限限制，无法取到完整内容。

该视频受权限限制（充电专属、仅预览），无法获取完整音频。
平台提示：为创作付费，购买观看完整视频|购买观看

可能原因：
  · 充电专属视频（需要给 UP 主充电后才能看完整版）
  · 付费/大会员专享内容
  · 仅提供试看预览

当前账号无权访问完整媒体流，因此无法生成完整逐字稿。
换一个有权限的账号，或换一个视频再试。
```

### 10.3 顺带修掉的两个隐患

1. **缓存会丢权限标记**。`video_info` 缓存只存了 7 个基础字段，
   读缓存时 `is_upower_exclusive` 等全部丢失 → 受限视频被当成正常视频，
   又回到"把预览当完整"那条路。现在缓存包含全部权限字段，
   且对**旧缓存**（缺字段）做了容忍 + 自动补查。
2. **`permission` 字段类型不一致**。实测它是字符串不是字典，
   而代码写了 `(data.get("permission") or {}).get("need_login")` → `AttributeError`。
   接口字段类型不是契约，已加类型分支。

### 10.4 新增的诊断工具（长期保留）

| 脚本 | 用途 |
| --- | --- |
| `scripts/probe_playurl.py` | 打印 playurl **原始响应** + 权限标记，判定"取不到音频"的真实原因 |
| `scripts/probe_durl.py` | 判断 durl 路线拿到的是**完整音频还是预览片段**（含 ffmpeg 带 Referer 探测） |

`probe_durl.py` 里踩到一个排查陷阱值得记：**ffmpeg 读 URL 必须传 Referer/UA**
（`-headers`），否则 CDN 返回 403，而 ffmpeg 只打印一行
`Server returned 403 Forbidden` —— 很容易被误读成"这个流没有音频轨"。
这两个结论的处置方式完全不同。
