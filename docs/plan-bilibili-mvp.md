## 一、结论

**技术全线可行，且已实测验证。** 三个曾被视为风险的点现在都有了明确答案：

1. **扫码登录** —— B 站官方扫码登录接口实测可用，能实现"弹二维码 → 手机扫码 → 本地存 session"，无需让用户手工复制 Cookie。这是让「别人也能用」成立的关键。
2. **转写兜底** —— 音频流匿名可下载（三 CDN 实测 HTTP 206），本地 ASR 路线成立。
3. **依赖获取** —— 唯一的坑是 GitHub / HuggingFace 直连不通，但已有等价替代方案（见 §3.4）。

**唯一需要立刻处理的既存问题**：你机器上的 torch 是 **CPU 版**，GPU 尚未启用（见 §3.3）。


**好消息**：CUDA 版 wheel 的下载源实测全部可达：

| 来源 | 结果 |
| --- | --- |

| `download.pytorch.org/whl/cu124` | ✅ 可达，但实测仅 0.25 MB/s |
| `mirrors.aliyun.com/pytorch-wheels/` | ⚠️ 可达，但实测仅 **0.19 MB/s**（2.5GB 要 3.6 小时，不可用） |
| `mirrors.tuna.tsinghua.edu.cn/pytorch-wheels/` | ❌ 该目录不存在 |
| `mirrors.bfsu.edu.cn/pytorch-wheels/` | ❌ 该目录不存在 |
| 清华 PyPI 镜像 | ❌ **只有 CPU 版**，装不到 CUDA 版 |

> 代价：CUDA 版 torch 约 **2.5GB** 下载量，首次环境准备主要时间花在这里。

> 三者必须配套锁死：

> **Content-Length 与实际文件长度**——我最初把它误判成了镜像问题。

## 四、B 站接口实测记录

### 4.1 ✅ 扫码登录：可用（本轮新增验证，最关键）

```
① GET passport.bilibili.com/x/passport-login/web/qrcode/generate
   → code=0
     qrcode_key = 5869e68e351526b5c7702249d5961b75
     url        = https://account.bilibili.com/h5/account-h5/auth/scan-web?...

② GET passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=...
   → code=0, data.code=86101, data.message="未扫码"   ✅ 符合预期
```

`data.code` 状态机（这是前端轮询要处理的四种状态）：

| code | 含义 | 前端动作 |
| --- | --- | --- |
| `86101` | 未扫码 | 继续轮询 ✅ 已实测 |
| `86090` | 已扫码待确认 | 提示"请在手机上确认" |
| `0` | 登录成功 | 响应头 `Set-Cookie` 携带 `SESSDATA`/`bili_jct`/`DedeUserID`，落库 |
| `86038` | 二维码失效 | 提示刷新二维码 |

**实现要点**：服务端把 `url` 给前端 → 前端渲染成二维码 → 服务端轮询 B 站 → 成功后从 `Set-Cookie` 取出凭证 → **加密存储到本地**，与用户身份绑定。无需任何手工复制 Cookie 的操作。

### 4.2 🔴 字幕接口：匿名拿不到，且是静默失败（**P0 已复现，形态比预想更隐蔽**）

对热门榜前 10 个视频逐个请求 `/x/player/wbi/v2`：

```
code=0  subs=0  allow_submit=False    × 10 / 10
```

**它是静默失败**：`code=0`、`message=OK`，不报错，只是字幕列表为空。**这是全方案唯一的高危陷阱** —— 不做校验的话，程序会"成功地"把每个视频处理成空文本，一路绿灯跑完，你拿到一堆空文件还查不出原因。

**P0 复现的完整形态**（见 [p0-findings.md](p0-findings.md) §3）：`subtitle` 字段**并没有缺失**，
它实实在在地返回了

```json
{"allow_submit": false, "lan": "", "lan_doc": "", "subtitles": []}
```

所以"字段缺失→报错"这种写法也拦不住它。判定必须结合 `nav` 的 `isLogin`：
**无登录态 + 空列表 = 无法判定**，只有**已登录 + 空列表**才能确认"该视频没有字幕"。

代码必须显式区分「该视频没有字幕」与「当前未登录 / 无权限」，并对逐字稿长度设下限校验。
已落地为 `NotLoggedInError` / `NoSubtitleError` 两种异常 + 8 条离线回归测试。


### 4.3 ✅ 音频流：匿名可下载（兜底路线成立）

```
GET api.bilibili.com/x/player/playurl?bvid=...&cid=...&fnval=16
→ code=0，DASH 音频 204kbps (mp4a.40.2)
```

三个 CDN 节点 Range 下载实测：

| CDN 主机 | 结果 |
| --- | --- |
| `...mcdn.bilivideo.cn`（P2P） | ✅ HTTP 206 |
| `...edge.mountaintoys.cn`（备用） | ✅ HTTP 206 |
| `upos-sz-mirrorcoso1.bilivideo.com`（官方） | ✅ HTTP 206 |

两个坑：必须带 `Referer: https://www.bilibili.com` + 浏览器 UA，否则 403；`HEAD` 请求在 P2P 节点返回 404，**只有 GET 正常**，排查时别被误导。

### 4.4 ⚠️ 风控：真实存在

```
GET /x/web-interface/ranking/v2 （无 Cookie） → code=-352 风控校验失败
先访问首页取得 buvid3 Cookie 后              → code=0 正常
```

对策：维持会话 Cookie、请求间隔 ≥0.5-1s、元信息本地缓存、失败指数退避。

### 4.5 CDN 可达性

`aisubtitle.hdslb.com` DNS 正常、根路径 403（正常现象非封禁）；`i0.hdslb.com` 200。**不存在网络层封锁。**

## 五、系统架构（Web 版）

### 5.1 整体形态

```
┌─────────────────────────────────────────────────────────┐
│  浏览器前端（贴链接 / 显示二维码 / 展示三件套产物）        │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP
┌────────────────────────▼────────────────────────────────┐
│  后端服务（FastAPI）                                     │
│                                                          │
│  ├─ 登录模块    扫码登录流程，session 加密落盘（按用户隔离）│
│  ├─ 取数模块    元信息 → 字幕(需登录) ─┬─ 命中 → 逐字稿     │
│  │                                    └─ 未命中 ↓         │
│  ├─ 转写模块    DASH音频 → imageio-ffmpeg → FunASR(GPU)  │
│  ├─ 总结模块    分段 → map 摘要 → reduce 合并 → DeepSeek  │
│  └─ 任务队列    GPU 串行调度 + 进度回报（WebSocket/轮询）  │
└────────────────────────┬────────────────────────────────┘
                         │
              data/ 产物（逐字稿 / 总结 / 要点 Markdown）
```

### 5.2 三个必须在架构层就定好的设计

**① GPU 是串行资源，必须有任务队列**
FunASR 占满显存，多人同时提交不能并发转写。需要一个队列（建议先用简单的进程内队列 + SQLite 持久化，别一上来上 Celery/Redis），前端显示排队位置与进度。

**② 逐字稿要带时间戳锚点**
总结与要点里每条结论都要能点回原视频位置。这不只是体验问题 —— 它决定了产物能否被信任和复用。

**③ 校验"空产物"，绝不静默放过**（对应 §4.2 的高危陷阱）
每个环节都要有产出校验：字幕为空 → 明确报"该视频无字幕，已转用语音识别"；ASR 结果过短 → 报失败；总结为空 → 重试。**宁可报错，不要给用户一个空文件。**

### 5.3 托管模式：代价清单（**本方案风险最集中的地方**）

你选择由自己托管服务，意味着定位从「个人工具」变成了「对外提供的服务」。技术上完全可行，但以下代价必须由你承担。**请逐条确认能接受再开工。**

**① 你要代管他人的 B 站登录凭证 —— 这是最大的责任变化**
自部署时凭证在用户自己机器上；托管后，**用户的 `SESSDATA` 存在你的服务器里**，等同于你保管一批他人账号的登录态。要求：加密存储（密钥与数据库分离）、最小留存、支持用户一键登出与吊销、明确告知用户。泄露一次，影响的是所有使用者。

**② GPU 算力 —— 主要成本**
- 云 GPU 按需实例（4090 / A10 级别）量级约 **¥1.5-4 / 小时**；若要 7×24 常驻，月成本量级 **¥1,000-3,000**（估算，需按实际供应商价目复核）
- 省钱替代：用你自己的 4070 Ti 托管 → 电费几乎可忽略，但要接受机器需常开机、家宽上行（通常 30-50Mbps，够用）、动态 IP / NAT 穿透、断电断网即服务不可用

**③ DeepSeek 费用 —— 反而很低，不是主要成本**
1 小时视频逐字稿约 1-1.5 万字 ≈ 2 万 token；map-reduce 阶段放大约 2-3 倍，即每视频约 4-6 万 token。按 deepseek-chat 公开价目量级估算约 **¥0.1-0.3 / 视频**（以官网价目为准，上下文缓存命中还能更低）。**真正吃预算的是 GPU，不是 LLM。**

**④ 带宽**
1 小时视频音频约 **90MB**（实测 204kbps 码率），由你的服务器下载后转写。按每天 100 个视频估算，流量量级约 9GB/天。

**⑤ 滥用与配额 —— 必须做，否则一定被刷**
开放注册 + 免费 GPU，必然被滥用。最低限度要有：账号门槛（邀请码）、每用户每日视频数配额、单视频时长上限（如 2 小时）、队列长度上限、失败重试上限。

> **P0 已按工作区主人指定细化并落地**（`src/vd/quota.py`）：
>
> | 登录身份 | 每日次数 | 当日累计时长 |
> | --- | --- | --- |
> | 主人自己的 B 站账号 | 不限 | 不限 |
> | 其他任何账号 | 3 次 | ≤ 3 小时 |
>
> 与原文的差别有两处，都更严格：配额**按登录的 B 站账号**计数（换浏览器、清 Cookie
> 无法绕过），且在**下载音频之前**判定（配额不足时不烧带宽、不占 GPU）。
> 次数与时长必须是**两道独立闸门**——否则"每日 3 个视频"会先把第 4 个挡掉，
> 导致"累计 ≤3 小时"这条规则永远不触发。


**⑥ 法律与合规 —— 性质变化，最需要你判断**
- 面向公众提供「把他人视频转成文字并总结」的服务，与个人学习研究性质不同；逐字稿属衍生内容，涉及 UP 主著作权
- B 站用户协议对自动化抓取与二次分发的限制，风险由你（服务提供方）承担
- 若视频含他人语音，还可能涉及个人信息
- 在国内公网对外提供服务，**通常需要 ICP 备案**（取决于服务器位置与是否公网开放）

**⑦ 折中建议**
若想先小范围验证价值，推荐：**邀请制、不公开收录、不对外分发逐字稿、显著免责声明 + 严格配额**。既保留「别人也能用」，又把风险控制在可承受范围。等验证有价值再考虑公开。

| **P3 Web 层** | FastAPI + 前端：扫码登录页、提交任务、进度、结果展示与下载；**账号体系与配额限流**（托管模式新增） | 3-4 天 | 可用的 Web 应用 ✅ **已完成**（见 [p3-web-layer.md](p3-web-layer.md)；含 SQLite 任务队列与单工作线程） |
| **P4 部署与运维** | 任务队列持久化、历史归档、用量统计与成本告警、Docker 化、免责声明与备案评估 | 3-4 天 | 可对外运行的托管服务 |

**为什么 P0 必须先做**：**字幕命中率**这个数字决定 P1 的重心。若 >70%，字幕为主、ASR 为辅；若 <30%，ASR 才是主干，值得花大力气调优（切句、标点、热词）。在不知道这个数字前写架构，是返工风险最高的做法。

> ⚠️ **P0 实测补充**：这个数字**必须在登录态下测**。匿名下所有视频都返回空列表，
> 测出的"命中率"恒为 0%，纯粹是未登录造成的，与字幕覆盖率无关。
> `scripts/hit_rate.py` 因此把 `not_logged_in` 单独计数，非零时会打印"命中率**不可信**"。
>
> **P0 实测结果：命中率 60%**（20 个视频，主人观看历史）→ 落在"混合策略"区间。
> 两个附加发现改变了 P1 的设计重心：
> 1. 命中的 12 个**全部是 B 站 AI 字幕，人工字幕 0 个** —— 站内字幕 ≈ B 站自己的 ASR。
> 2. 两条路线的**专有名词错误属同一类**（B 站："DeepSeek"→"DPCARNE"；
>    本地："花鼓灯"→"花舞灯"）。
>
> 因此：**字幕优先的真正理由是零 GPU 成本**（同等质量下不占显存）；
> 热词表与后处理必须两条路共用一份。详见 [p0-findings.md](p0-findings.md) §7。

| **R1** | 字幕接口**静默返回空**，会把"无权限"误判成"无字幕" | 🔴 高 | 显式区分二者；逐字稿长度下限校验；**宁报错不产空** |
| **R2** | torch 当前为 CPU 版，ASR 慢到不可用 | 🔴 高 | 装 CUDA 版 torch（阿里云 pytorch-wheels 镜像）；注意 torch/torchaudio/CUDA 三者版本匹配 |
| **R3** | 登录 session 等同账号凭证，多人使用需隔离 | 🔴 高 | 按用户隔离存储、加密落盘、不入版本库；提供登出与吊销；如自部署则风险归使用者 |
| **R4** | 风控 `-352` / `412`（已复现） | 🟡 中 | 会话 Cookie（`buvid3`）、限速 ≥0.5-1s、元信息缓存、UA/Referer 齐全、指数退避 |
| **R5** | 字幕覆盖率无保证 | 🟡 中 | ASR 作一等公民；P0 先测出真实命中率 |
| **R6** | GitHub / HuggingFace 不通 | 🟡 中 | ffmpeg 用 PyPI `imageio-ffmpeg`；模型走 ModelScope / hf-mirror |
| **R7** | GPU 显存竞争，多任务并发崩溃 | 🟡 中 | 任务队列串行化；显存不足时降级到 paraformer-small |
| **R8** | FunASR / torchaudio 与 Python 3.13 兼容性未验证 | 🟡 中 | P0 首要验证项；若不兼容，装一个 3.11/3.12 专用于本项目 |
| **R9** | 长视频超上下文，总结漏信息 | 🟢 低 | map-reduce 分段 + 时间戳锚点回溯 |
| **R10** | 版权与合规（托管后性质变化） | 🔴 高 | 邀请制、不公开收录、不二次分发逐字稿、显著免责声明（详见 §5.3⑥） |
| **R11** | **代管他人 B 站凭证**，一旦泄露影响所有使用者 | 🔴 高 | 加密存储、密钥与数据库分离、最小留存、一键吊销、明确告知用户 |
| **R12** | 服务被滥用（免费 GPU + 免费 Key 必然被刷） | 🔴 高 | 邀请制、每用户配额、单视频时长上限、队列与重试上限 |
| **R13** | GPU 成本失控 | 🟡 中 | 用量统计 + 预算告警；按需启动而非 7×24 常驻；或考虑本地 4070 Ti 托管 |
| **R14** | 家宽托管不稳定（动态 IP / NAT / 断电断网） | 🟡 中 | 用云 GPU，或明确接受服务存在不可用窗口 |

**建议**：P0 阶段顺手用 VideoCaptioner 跑一个视频做对照，成本很低，还能交叉验证字幕路线与产物质量预期。
